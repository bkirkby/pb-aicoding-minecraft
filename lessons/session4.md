# Session 4 — A Brain for the Pet

A program by [Pheirce Bytes](https://www.pheircebytes.com/ai-consulting), in partnership with [Bright Tomorrow](https://www.brighttomorrowmath.com/).

Until now the pet says lines you wrote. Today it starts making its own. You'll run a small language model on your own laptop, talk to it directly, and then wire the pet up to it so its replies are generated on the spot. The lines you wrote don't go away: they become the fallback for when the model isn't there.

This is a big change, so it's two sessions. Today: get a model running locally, design how the mod should use it, and make the pet say one generated line with a safe fallback. Next session: teach the mod to find, download, and start the model on its own, and give the pet a real personality.

This assumes session 3 is done: the pet has canned dialogue in your own voice, and `PLAN.md` has a "How it should feel" section.

## Before the session (instructor)

Two downloads, both too big to do on class wifi. Get them onto the machine ahead of time, in a folder like `devel\llm`:

1. **llama.cpp**, the program that runs the model. Grab the latest Windows release zip from the llama.cpp GitHub releases page. Use the **CPU** build: it works on every machine, and the course is built around it. (The GPU builds are faster on machines that have one, and that's a conversation for later in the session, not a setup step.) Unzip it.
2. **The model file.** The course uses **Phi-3.5 mini Instruct**, Q4_K_M, in GGUF format. It's about 2.4 GB, has about four billion parameters, and runs acceptably on a CPU. Download it from its Hugging Face page and put it next to the llama.cpp folder.

Test it once before class: in PowerShell, from the unzipped folder, run

```
.\llama-server.exe -m ..\model.gguf
```

and open `http://localhost:8080` in a browser. If you get a chat page and it answers, you're ready.

## Step 2 — Meet the small model

Open the **PowerShell** shortcut. Go to the llama.cpp folder and start the server:

```
cd ..\llm\llama.cpp
.\llama-server.exe -m ..\model.gguf
```

(Your instructor will tell you the exact folder names.) It takes a few seconds to load the model into memory. When it says it's listening, open a browser and go to `http://localhost:8080`. That's a chat page, served by the program you just started, on your own computer.

Talk to it. Ask it things. Notice:

- **It's slow.** The words trickle out. That's your laptop doing the math, not a data center.
- **It's not as smart as the AI in opencode.** Ask it something hard and it'll get it wrong, confidently. That AI has hundreds of times more parameters and runs on machines the size of a room. This one fits in about 2.4 GB.
- **It works with the wifi off.** Try it. Turn off wifi, ask it something, turn wifi back on. Nothing you type leaves the laptop.

Now the important experiment. The chat page has a place to set a **system prompt**: instructions the model reads before every conversation. Put the pet in there. Something like:

```
You are a wolf named Ash who was just given a potion that let you think and
speak for the first time. You are loyal, a little confused, and curious about
everything. Answer in one or two short sentences. Never say you are an AI.
```

Use your own pet's voice from session 3. Then ask it things a player would ask: "Who are you?" "Are you hungry?" "What's the meaning of life?" "Are you a robot?"

Some answers will be great. Some will break character. Fix the prompt and try again. You're doing the design work for next session right now, with no code at all. Save the prompt you like best; ask opencode to put it in `NOTES.md`.

Leave the server running.

## Step 3 — Design it before you build it

Press **Tab** to switch opencode to **plan** mode. This is a session 1 conversation: describe what you want, say what's fixed, and ask what you've missed.

```
I want the pet's dialogue to be generated by a local language model instead
of the canned lines. There's a llama.cpp server running at localhost:8080
with Phi-3.5 mini loaded. Facts:

- The canned lines stay. They're the fallback whenever the model isn't
  running, is too slow, errors, or gives a bad answer. The pet must always
  say something.
- The game must never freeze while the pet is thinking.
- The player should be able to say things to the pet and get a reply.
- For today, assume the server is already running. Next session we'll make
  the mod find and start it itself.

How would you structure this, what could go wrong, and what's the smallest
piece we could get working first?
```

Read it carefully. Things it should bring up, and that you should ask about if it doesn't:

- **How the mod talks to the server.** Over HTTP on your own machine, the same way a browser talks to a website. It'll send a request with the prompt and get back text.
- **Off the game thread.** Minecraft draws the world many times a second on one thread. If the mod waits for the model on that thread, the whole game freezes for a second or more. The request has to happen on the side, and the pet speaks when the answer comes back.
- **When to fall back.** Server not there. No answer after a few seconds. An error. An answer that's empty, or way too long, or says "as an AI language model." Each of those should quietly use a canned line instead.
- **How the player talks to the pet.** A chat message when the pet is nearby? A message that starts with its name? Right-clicking opens something? This is a design call, and it's yours.
- **What goes in the prompt.** The system prompt from step 2, plus whatever the player said. Maybe the pet's name, the time of day, whether it's hurt. More context makes better replies, but every word costs time.

Push back where you disagree. When it's settled:

```
Write this into PLAN.md as a new section called "The pet's brain." Include
the fallback rules and what we decided about how the player talks to the
pet. Mark the detect-and-download part as next session.
```

## Step 4 — The smallest piece, with the fallback

**Tab** back to **build**.

```
Build the smallest piece: when the player right-clicks the sentient pet, ask
the model for one line using the system prompt in NOTES.md, and have the pet
say it. If there's no answer within a few seconds, or anything goes wrong,
say a canned line instead. Don't build the player-talks-to-pet part yet.
```

When it builds, launch the game, get a pet and a potion (the [cheat sheet](../guides/test-commands.md) has the commands), wake it, right-click. There'll be a pause, then a line nobody wrote. Do it a few times. It's different every time.

Now the test that matters more than the first one. Go to the PowerShell window and press **Ctrl+C** to stop the server. Back in the game, right-click the pet.

It should still speak, with one of your canned lines, and the game should not have hiccupped. If it froze, or the pet said nothing, or the game crashed, that's today's bug report, and it's the most important one in the mod. A pet that only talks when everything is perfect is a pet that's silent most of the time.

Start the server again. Right-click the pet. It should go back to generated lines without restarting the game.

## Step 5 — Let the player talk

```
Now let the player talk to the pet, the way we decided in PLAN.md. Build it.
```

Test it. Say things to the pet. Say things a player would actually say, including rude things and nonsense. Watch what comes back.

You'll notice two kinds of problems:

- **Code problems.** It freezes, it doesn't reply, it replies twice, it replies to everyone's chat. Bug report, fix, rebuild.
- **Prompt problems.** It's out of character, it's too long, it's boring, it calls itself an assistant. Those aren't code. Those are the system prompt, and they're next session's work. Note them in `NOTES.md` and move on.

Also notice the pause before it answers. That's real now, not a design choice. If it feels like the pet is thinking, good. If it feels like the game is broken, tell the AI: "The pet needs to show it's thinking while it waits."

## What you should walk away with

- A small language model running on your own laptop, and a feel for how it differs from the big one
- A system prompt that makes it sound like your pet, tested before any code existed
- The pet saying generated lines in the game, with your canned lines as the fallback
- The fallback proven: server off, pet still talks, game doesn't freeze
- Two new words: **fallback** and **off the game thread**

## Things that might go wrong

**llama-server won't start, or exits right away.** If it complains about memory, the model is too big for the machine: try a smaller one, like a 1B or 2B model, which is under 1.5 GB. If you tried a GPU build, go back to the CPU build.

**It's painfully slow.** CPU-only laptops manage a few words a second on Phi. That's usable for one-line replies. If it's worse than that, try a smaller model. If the machine has a real GPU, the talking points cover trying a GPU build with `-ngl 99`. Speed versus smarts is the tradeoff; a pet doesn't need to be smart.

**The game freezes every time the pet thinks.** The request is running on the game thread. Report it exactly that way: "The game freezes for about two seconds when I right-click the pet, then it speaks. The request needs to be off the game thread." The AI knows what that means.

**The pet says "As an AI language model..."** Prompt problem, not code. Add "Never say you are an AI or a language model" to the system prompt and, for today, have the fallback catch replies containing "AI" or "language model." Proper personality work is next session.

**Windows asks whether to allow llama-server through the firewall.** It's only listening on your own machine. Allow it, or cancel; either way it works for localhost.

**The pet replies to everyone's chat, or to its own lines.** Design bug from step 3. Go back to how the player talks to the pet and tighten it: only messages from the pet's owner, only when nearby, only when they start with its name.

It'll check whether llama.cpp and the model are on the machine, download them if not, with a message and progress in the game, and start the server itself, falling back to canned lines at every step where something's missing.
